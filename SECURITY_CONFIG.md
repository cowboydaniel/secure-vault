# Security Configuration Baseline

This guide defines the operational baseline for SecureVault deployments. It covers
filesystem permissions, supported environment variables, and the hardening
checklist that operators must acknowledge before going live.

## File Permission Baseline

| Component | Recommended Mode | Rationale |
| --- | --- | --- |
| `~/.config/secure_vault/` (InstanceGuard state directory) | `0700` | Only the service account should be able to read tamper metadata. Created with owner-only permissions during initialization. |
| `~/.config/secure_vault/instance_state.json` | `0600` | Contains binding secrets for tamper detection and is written with owner-only access. |
| Authentication database (`users.db` or custom path) | `0600` | Stores credentials, salts, and audit metadata. The database handler enforces owner read/write only. |
| `~/.secure_vault/` (secret material directory) | `0700` | Holds peppers and other authentication secrets. Created with owner-only permissions. |
| `~/.secure_vault/email_pepper.key`, `session_pepper.key` | `0600` | Random peppers generated if environment overrides are absent. Files are restricted to the owner. |
| Key metadata file and automatic backups | `0600` | Metadata and backup JSON files are saved with owner-only permissions to prevent disclosure. |
| Storage root and internal subdirectories | `0700` | Storage engine bootstraps all container, fragment, steganography, temp, and backup directories with owner-only access. |
| Storage marker (`.secure_vault`) and salt (`.system_salt`) files | `0600` | Identifiers and salts generated by the storage layer are locked to the service account. |
| Generated share outputs (`*_share_*.sec`) | `0600` | Share artifacts produced during encryption are chmodded to owner read/write only. |

> **Note:** Ensure the process `umask` preserves these settings (`umask 077` is
> recommended) when running SecureVault under supervisors or service managers.

## Environment Variables

| Variable | Purpose | Recommendation |
| --- | --- | --- |
| `SECURE_VAULT_STATE_DIR` | Overrides the InstanceGuard state directory. | Point to a root-owned, encrypted location or accept the default `~/.config/secure_vault/` with mode `0700`. Never use world-readable paths. |
| `SECURE_VAULT_EMAIL_PEPPER`, `SECURE_VAULT_SESSION_PEPPER` | Provide base64-encoded peppers instead of on-disk secrets. | Inject via a secret manager (KMS, vault, etc.). Avoid storing literal values in shell history or unit files. |
| `PKCS11_TESTS` | Enables PKCS#11 hardware tests. | Keep unset in production. Use secure CI secrets when exercising hardware-backed flows. |
| `PKCS11_LIBRARY`, `PKCS11_SLOT`, `PKCS11_PIN` | Configure PKCS#11 sessions. | Store in a hardware secret manager or inject via temporary environment files with restrictive permissions. Rotate the PIN after testing. |

## Hardening Checklist

Operators must tick each item prior to deployment and archive the signed copy
with the change record.

- [ ] Confirm the InstanceGuard directory and state file match the [file permission baseline](#file-permission-baseline) and reside on protected storage.
- [ ] Confirm the authentication database (`users.db` or custom path) is owner-only (`0600`) and backed up to an encrypted location.
- [ ] Confirm the secret material directory (`~/.secure_vault/`) is `0700` and all pepper files are `0600`, or inject peppers via secure environment variables.
- [ ] Confirm key metadata and backup directories enforce owner-only file permissions, and retention settings delete stale copies.
- [ ] Confirm storage directories (including `containers/`, `fragments/`, `steganography/`, `temp/`, and `backup/`) inherit `0700` permissions and generated shares are `0600`.
- [ ] Confirm `SECURE_VAULT_STATE_DIR` is set (if overridden) to a non-world-readable path stored on trusted media.
- [ ] Confirm all security-sensitive environment variables are supplied through your organization's approved secret distribution mechanism and are cleared from the process environment after use.
- [ ] Confirm PKCS#11 configuration variables are scoped to operators performing HSM work and rotated after validation.
